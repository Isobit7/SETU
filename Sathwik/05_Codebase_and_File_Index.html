4. Cloud GPU Training Guide (Google Colab / AWS)

To retrain models on high-volume datasets (such as the 42,000 ISL image dataset) without local thermal throttling, SETU provides dedicated cloud training pipelines in scripts/:

Google Colab 1-Click Notebook

scripts/train_isl_cloud_colab.ipynb: Fully automated Jupyter notebook designed for free T4 or A100 GPU instances. Ingests raw images, extracts 126-D landmarks, trains with AdamW and cosine decay, and exports realsign_26class_mlp.pth.

Headless Python Trainer

scripts/train_isl_cloud.py: Standalone command-line trainer supporting multi-GPU distributed data parallel (DDP), mixed precision (FP16), and automatic dataset manifest validation.

5. Comprehensive Technical Viva & Exam Defense (25 Questions)

Q1: What fundamental problem does Project SETU solve?

Answer: SETU bridges the communication gap between over 18 million Deaf/hard-of-hearing individuals in India and hearing citizens. It provides real-time, bidirectional translation between Indian Sign Language (ISL) gestures and natural English text/speech using standard, ubiquitous consumer webcams without requiring expensive sensory hardware.

Q2: How does Indian Sign Language (ISL) differ fundamentally from American Sign Language (ASL)?

Answer: ISL has three crucial differences: (1) Bimanual Fingerspelling: While ASL alphabet signs are primarily one-handed, authentic ISL letters (B, D, P, Q, T) require coordinated contact between both hands. (2) SOV Grammar: ISL uses Subject-Object-Verb syntax rather than English SVO. (3) Non-Manual Markers: Facial expressions and eyebrow movements serve as grammatical question markers.

Q3: Why does SETU use MediaPipe skeletal landmarks rather than raw RGB pixels or 3D CNNs?

Answer: Feeding raw pixels into CNNs makes models brittle to room lighting, skin complexions, clothing, and background clutter. Extracting 3D skeletal landmarks compresses a 921,600-byte frame into a compact, normalized vector, achieving complete background invariance and sub-millisecond inference latencies suitable for real-time edge execution.

Q4: What is the exact mathematical formulation of wrist normalization in SETU?

Answer: (1) Translation: Shift wrist to origin: $\mathbf{p}' = \mathbf{p} - \mathbf{p}_{\text{wrist}}$. (2) Scale: Divide all points by rigid palm distance $d = \|\mathbf{p}_9' - \mathbf{p}_0'\|_2$. (3) Rotation: Rotate around Z-axis by $\theta = \operatorname{atan2}(-v_x, -v_y)$ to align palm with the vertical axis, followed by X-axis rotation $\phi = \operatorname{atan2}(v_z, -y_{\text{rot}})$ to cancel out camera pitch.

Q5: What are the differences between 126-D, 134-D, 158-D, 164-D, and 328-D feature vectors?

Answer: (1) 126-D: Dual-hand landmarks ($21 \times 3 \times 2$) for RealSign A–Z. (2) 134-D: AI4Bharat INCLUDE schema (50 pose + 42 LH + 42 RH scaled to 1920×1080). (3) 158-D: Base holistic vector (63 RH + 63 LH + 24 pose + 8 face). (4) 164-D: 158-D base + 6 facial expression ratios (zero-filled when face mesh is absent). (5) 328-D: 164 coordinates/ratios + 164 finite-difference velocity features.

Q6: Why are 134-D and 158-D features strictly separated in the codebase?

Answer: They represent fundamentally different coordinate spaces. 134-D contains unnormalized pixel coordinates scaled to $1920 \times 1080$ for the AI4Bharat Zenodo benchmark model. 158-D contains unit-normalized wrist-centered landmarks for SETU's internal models. models/adapters/include.py enforces an explicit assertion preventing 158-D features from ever being passed to the 134-D model.

Q7: What happens to the six facial expression features in 164-D when MediaPipe Face Mesh is not detected?

Answer: When Face Mesh is unavailable, all six facial expression dimensions (indices 158..163) are explicitly zero-filled. The server code guarantees that unmeasured facial expressions are never fabricated or presented as real physical measurements.

Q8: How does the BiLSTM model dynamic temporal sequences?

Answer: It processes a rolling FIFO sequence of 30 frames. For each frame, it computes first-order velocities $\mathbf{V}_t = (\mathbf{F}_t - \mathbf{F}_{t-1}) / \Delta t$ across 164 features, forming a $(30, 328)$ spatiotemporal matrix that captures both joint positions and movement trajectories.

Q9: What is Connectionist Temporal Classification (CTC) Greedy Decoding, and why is it used?

Answer: In continuous sign language, a user holds a sign across several consecutive frames. CTC greedy decoding identifies continuous blocks of identical class predictions, eliminates duplicate consecutive tokens, and removes no_sign blank tokens, converting raw frame streams into discrete word tokens without requiring manual frame segmentation.

Q10: How does YOLO-World v2 run without dropping the 30 FPS landmark tracking rate?

Answer: YOLO-World v2 runs in a non-blocking asynchronous executor thread (loop.run_in_executor). The sign language landmark thread never awaits the object detector. It checks for finished detection results every 6 frames, allowing the main sign recognition loop to sustain a consistent 28–30 FPS.

Q11: Why is Qwen2.5-0.5B classified as a decoder-only causal language model rather than Seq2Seq?

Answer: The imported model class is AutoModelForCausalLM, which is an autoregressive decoder-only Transformer. While the application task is sequence-to-sequence translation, the neural architecture predicts tokens causally from left to right using a ChatML prompt rather than an encoder-decoder cross-attention structure.

Q12: How does the temporal debouncing state machine prevent repeated letter flickering?

Answer: It requires a sign to maintain identical top-1 classification for at least 3–4 consecutive frames, requires a confidence margin $\ge 0.05$ over the second candidate, and engages a repeat lock. To sign identical consecutive letters (like "LL"), the signer must execute an idle baseline transition (such as a hand drop or relaxation).

Q13: How does SETU handle left-handed signers?

Answer: In models/adapters/realsign.py, when dual hands are detected, the classifier evaluates both the default orientation and a horizontally mirrored and slot-swapped configuration ($x \to -x$, Left Hand ↔ Right Hand). If the mirrored pass yields higher softmax margin, it accepts the mirrored prediction natively.

Q14: How does the neuro-symbolic heuristic tie-breaker resolve subtle finger curls?

Answer: On ambiguous classification boundaries (such as O vs C), the system evaluates exact physical landmark geometry: fingertip-to-thumb closure distance $\|\mathbf{p}_8 - \mathbf{p}_4\|_2$ (<0.32 → closed ring O; ≥0.38 → open curve C) and index-middle spread angle (<8.5° → parallel U; ≥13° → spread V).

Q15: What is the true source and meaning of the 94.99% RealSign accuracy?

Answer: 94.99% is the checkpoint-reported test accuracy stored in realsign_26class_mlp.pth evaluated across 3,120 held-out static landmark feature vectors. It is an offline evaluation metric on isolated vectors, not live application streaming accuracy.

Q16: What is the source and meaning of the 0.562386... INCLUDE checkpoint score?

Answer: 0.5623867753623188 is a scalar score stored directly inside the AI4Bharat checkpoint dictionary. Because the original evaluation harness is external, it is documented strictly as a checkpoint-stored score with its metric definition unverified.

Q17: Does SETU use any SQL relational database at runtime?

Answer: No. SETU uses zero runtime SQL databases. All datasets and model features are stored in compressed NumPy archives (.npz), cryptographic JSON split manifests, and directory-based session captures on disk.

Q18: How does SETU prevent data leakage in its training datasets?

Answer: In data/manifests/realsign_clean_manifest.json, samples are strictly stratified by signer identity using SHA-256 cryptographic hashes. All frames from a given signer are assigned exclusively to either the training set or the testing set, preventing artificially inflated accuracy.

Q19: What is WebSocket backpressure protection, and why is it essential?

Answer: If a client camera sends frames faster than the backend can decode them, frames accumulate in the network buffer, causing latency to drift by several seconds. The backpressure guard drains stale queued frames and decodes only the freshest received frame.

Q20: How does the system guide users who sign outside the camera frame or in low light?

Answer: VisualFramingGuide.tsx computes facial brightness and shoulder span centering. If lighting falls below 0.38 or the user's upper body is off-center, real-time visual banners notify the user (“Move closer”, “Low light detected”).

Q21: What is the purpose of the 10-step execution lifecycle?

Answer: It provides a deterministic, decoupled processing contract that isolates camera ingress, landmark extraction, spatial normalization, neural inference, debouncing, causal translation, and audio synthesis into testable pipeline stages.

Q22: What are the primary latency bottlenecks on CPU versus CUDA hardware?

Answer: On CUDA GPUs, total end-to-end latency is ~14–20 ms (50+ FPS). On pure CPU, Qwen2.5-0.5B causal generation increases from 35 ms to 250–600 ms, which is mitigated by running translation in background threads and using immediate title-cased join fallbacks.

Q23: How does the custom sign dataset recording endpoint function?

Answer: POST /api/v1/dataset/record_sample accepts a 30-frame sequence of 164-D vectors or landmarks, pads missing facial ratios with zeros, validates array finiteness, and saves a timestamped custom_ archive for future fine-tuning.

Q24: What ethical considerations exist in sign language AI tools?

Answer: Tools must respect the linguistic sovereignty of Deaf communities, avoid misrepresenting fingerspelling as full grammatical fluency, prevent non-consensual biometric data capture, and transparently document confidence thresholds to avoid dangerous misinterpretations in critical domains like healthcare.

Q25: How does SETU guarantee offline-first operation?

Answer: All PyTorch weights, MediaPipe models, Qwen language model checkpoints, and Web Speech API synthesis operate entirely locally without requiring internet connectivity, cloud API tokens, or external CDN dependencies.
